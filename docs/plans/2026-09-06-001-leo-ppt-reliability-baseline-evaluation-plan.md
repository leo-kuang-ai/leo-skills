# Leo PPT Generator 高可靠正式交付基线测评方案

## 目标

建立一套可重复、可审计、能反映真实交付风险的基线测评，回答：

> `leo-ppt-generator` 在真实材料、真实 Provider、真实 PPTX 渲染环境和人工验收下，能否稳定交付完整、准确、可读、可编辑且可恢复的演示文稿？

本方案用于建立基线和失败分布，不直接修改 Skill 实现，也不把静态规则通过率当作交付可靠性结论。

## 评价对象与边界

### 纳入范围

- `generate` 图片式路线；
- `direct-editable` 可编辑路线；
- `hybrid` 混合路线；
- 内容合同、来源和数字保真；
- 风格、布局、容量和渲染；
- Provider、worker、重试、恢复和部分失败；
- PPTX、PDF、演示软件打开和人工验收；
- 成本、耗时、返工和交付后缺陷。

### 不纳入范围

- 新增行业规则；
- 扩大 Provider 或模型数量；
- 优化提示词但不改变测量设计；
- 平台发布、外部代发和用户业务决策；
- 用合成评分替代逐页证据。

## 基线测评原则

1. **真实路径优先**：必须经过实际 runtime、Provider、PPTX 导出和目标查看器。
2. **固定输入可复现**：每个 fixture 固定版本、哈希、材料来源和预期答案。
3. **逐页记录**：套件级通过不能掩盖单页严重错误。
4. **事实与呈现分开判定**：数字正确、图表语义、版式可读性和可编辑性分别记录。
5. **严重度优先**：一个事实或合规错误不能被大量低风险页面的平均分抵消。
6. **证据分层**：区分设计意图、静态检查、现场运行、人工验收和交付后反馈。
7. **不因测评改输入**：基线阶段禁止为通过而改写材料、放宽规则或手工修图。

## 测试矩阵

### 行业与任务

| 组别 | 典型任务 | 关键风险 |
|---|---|---|
| 管理汇报 | 经营复盘、季度决策汇报 | 结论不清、证据断裂、页间重复 |
| 财务/融资 | 经营数据、融资材料、私募说明 | 数字、单位、比例、免责声明错误 |
| 学术/科研 | 论文答辩、组会、文献汇报 | 图表、公式、引用、推导链失真 |
| 医疗/政府 | 方案汇报、政策或项目说明 | 敏感数据、合规措辞、排序逻辑 |

每组至少 3 套 deck：短 deck（6–8 页）、标准 deck（12–16 页）、密集 deck（25–40 页）。其中至少一套包含已知缺失来源、冲突数字、表格和长文本，用于验证失败是否被正确阻断。

### 路线与页型

每套材料至少覆盖：封面、结论页、文字密集页、数据图表页、表格页、引用页、图片页、收束页。每组至少有一套同时跑 `generate`、`direct-editable` 或 `hybrid` 中适用的两条路线，比较路线选择是否符合数据密度和交付要求。

### 扰动场景

- Provider 超时、限流、空输出和错误返回；
- 单页失败、批次失败、进程中断后恢复；
- 已完成页与未完成页混合清扫；
- 字体缺失、中文换行变化、图片不可读；
- 输入材料版本变化、来源清单漂移、收据篡改；
- 真实查看器打开、PDF 导出和投屏尺寸变化。

## Fixture 设计

每个 fixture 建立独立目录，至少包含：

- `input/`：原始材料、图片、表格和用户约束；
- `expected/`：事实答案、页级必现文本、图表语义和敏感字段；
- `manifest.json`：来源、版本、哈希、行业、页数和路线；
- `rubric.md`：人工验收标准和严重度定义；
- `known-failures.md`：故意注入的风险及预期阻断行为。

Fixture 必须记录材料是实测、用户确认、估算、示意或 unknown；禁止把预期答案写成未有来源的业务事实。

## 指标体系

### 交付结果指标

- **端到端成功率**：通过结构、渲染、事实、人工验收并形成完整交付收据的 deck / 总 deck。
- **严重错误率**：含 P0/P1 错误的 deck / 总 deck。
- **逐页缺陷率**：存在任意缺陷的页 / 总页数。
- **首次通过率**：无需内容或渲染返工即通过的页和 deck 比例。
- **返工率与返工轮次**：发生修订的页比例及 P50/P95 轮次。
- **恢复一致性**：恢复前后内容、页集合、风格、布局和指纹一致的比例。
- **交付后缺陷率**：人工验收后在目标查看器或真实使用中发现的问题比例。

### 可靠性与运营指标

- Provider 按页型的一次通过率、超时率、重试率和空输出率；
- P50/P95/P99 的耗时、成本和 token；
- 失败定位准确率：最终报告是否指向实际失败阶段；
- 错误恢复成功率及重复计费率；
- 人工确认耗时和确认后返工率；
- 交付收据、来源清单、渲染预览和模板样式源的完整率。

## 缺陷严重度

| 等级 | 定义 | 处理 |
|---|---|---|
| P0 | 事实、合规、敏感数据或页集合错误，导致不可交付或误导决策 | 立即阻断交付 |
| P1 | 关键页面不可读、图表语义改变、恢复后内容漂移、核心页缺失 | 不得声明完成，进入修复 |
| P2 | 明显布局、字体、视觉层级或可编辑性问题，影响正式使用 | 记录并按阈值决定返工 |
| P3 | 轻微间距、装饰或文案瑕疵，不影响理解 | 汇总观察，不用于掩盖高等级缺陷 |

同一页多个缺陷按最高等级计入；P0/P1 不得被平均分抵消。

## 执行阶段

### 阶段 0：冻结基线

冻结 Skill commit、runtime identity、Provider、模型、字体、查看器、操作系统、fixture 哈希和评测脚本版本。任何环境变化都建立新批次。

### 阶段 1：静态合同检查

运行现有结构、来源、数字、容量、样式、交付收据和评测入口检查。此阶段只建立“规则符合度”，不能作为真实可靠性结论。

### 阶段 2：小样本现场烟测

每个行业运行 1 套短 deck，确认 Provider、渲染链、查看器和人工验收通道可用。烟测失败时记录环境阻塞，不把整套基线标为 Skill 失败。

### 阶段 3：完整基线运行

按矩阵运行所有 fixture，保存每页 prompt、backend、QA、record、渲染预览、OCR 摘要、来源和收据。禁止中途手工修复后继续计入首次通过率；修复后的结果另记为返工批次。

### 阶段 4：故障注入与恢复

在固定页边界注入超时、进程中断、单页失败、输入漂移和收据篡改，验证系统是否只重派必要页面、保持已完成页稳定、给出可执行续点，并拒绝不一致交付。

### 阶段 5：独立人工验收

至少两名评审者按 rubric 独立检查事实、图表语义、可读性、可编辑性、行业适配和演示完整性。分歧保留原始意见，由第三方裁决，不用多数票抹平 P0/P1。

### 阶段 6：基线报告

报告必须同时提供：汇总指标、逐 deck 结果、逐页缺陷账本、失败阶段、严重度、成本耗时、恢复结果、人工分歧、未运行项和环境限制。

## 验收门槛建议

首轮只用于测量，不把以下数值当作已验证事实。建议在数据收集后由 Owner 冻结正式门槛：

- P0：0；
- P1：0 才能进入正式交付候选；
- 来源或数字不可追溯：0；
- 页集合缺失或恢复漂移：0；
- 目标查看器无法打开：0；
- 首次通过率、P95 耗时、P95 成本：按行业和路线分别设定，不合并平均；
- P2/P3：按交付档位设上限，并要求所有豁免有记录。

## 结果解释规则

- 静态检查全绿、现场失败：结论为“规则完整但交付可靠性未达标”；
- Provider 失败集中且换路线后消失：优先修复 backend 路由或能力选择；
- 数字正确但图表语义错误：优先修复确定性渲染和跨层验收；
- 视觉通过但行业评审拒绝：优先修复内容合同和行业论证，而不是继续调样式；
- 恢复失败或收据漂移：优先修复状态与账本一致性；
- 人工确认成本过高且缺陷下降有限：评估删除无效门禁或合并确认节点。

## 交付物

- `baseline-inventory.md`：fixture、环境和版本账本；
- `baseline-run.jsonl`：运行级和页级事件；
- `defect-ledger.csv`：缺陷、严重度、证据和处置；
- `review-rubric.md`：人工验收标准；
- `reliability-baseline.md`：指标、分组结果和限制；
- `retest-plan.md`：按最高影响失败排序的下一轮验证计划。

## 当前最大未知项

本方案完成前，不能确认最大短板究竟是 Provider 不稳定、渲染与版式、内容事实链、恢复机制，还是人工协作复杂度。基线测评的首要任务就是把这些候选原因分离，并用真实失败证据排序。
