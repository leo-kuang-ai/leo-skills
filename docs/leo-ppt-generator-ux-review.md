# leo-ppt-generator 用户体验评审（多智能体审查）

- 日期：2026-08-27
- 方法：三个独立审查代理分别走查**黄金路径**（新手首次使用旅程）、**失败与阻断旅程**（含 evaluation workspace 中 6 份模型真实回复的实证文案分析）、**交互设计与行业对照**（Gamma/Copilot/Canva 心智模型），交叉印证后合并；辅以行业调研（确认疲劳研究、agent UX 审批模式、渐进细化模式）。
- 结论速览：该产品的失败处置架构（单一 next_action、诚实负报告、"旧物未损"安抚）有多处达到专业水准；三类结构性体验问题是本评审核心产出——**黄金路径六轮才见第一张图、worker 缺失构成无解释死局、机器词表全程裸奔**。全部建议均在不削弱四条硬约束（Gate 0 阻断、样张门、真实派发、completed≠闭环）的前提下设计。

## 1. 三方共识：三个结构性问题

### 问题一：确认序列把 80% 决策压到第一页出现之前（痛感第一）

三方证据完全一致：

- 黄金路径走查实测：从提交需求到第一次看到任何视觉产物（样张）最早需要 **6 轮对话**——需求提交→大纲确认→完整逐页稿确认→视觉方向选择→backend 确认→样张确认（`references/image-deck-workflow.md:8-14`）；若输入同时含内容稿与视觉稿，还前置一轮路由问答。
- 文档没有任何条款允许把相邻确认门**合并为同轮**（如大纲+视觉方向一次给出）——这是流程解读层的额外税，不是质量合同的要求。
- 逐页稿确认（第 3 轮）阅读负担最重却发生在**零视觉参照**下，用户不知道自己该花多大力气审。
- 行业对照：[Gamma 的签名流程](https://gamma.app/)恰是一个轻量检查点（大纲确认）而非每步审批；[agent UX 模式目录](https://www.smashingmagazine.com/2026/02/designing-agentic-ai-practical-ux-patterns/)的原则是"审批只保留给不可逆操作，其余用 undo"。

### 问题二：worker 缺失是一个"不被允许解释的死局"（伤害第一）

- 统一阻断话术 `提供可调用的 worker 能力后从逐页派发阶段恢复` 对普通用户既不可理解也不可执行（不知道 worker 是什么、更不知道怎么"提供"）；
- 同一条款又禁止 Agent 枚举、诊断宿主能力来解释缺失原因——禁令本身是防内部信息泄漏的安全红线（评测判官设有泄漏红线），但两股力量叠加后用户撞上一堵不能获得任何解释的墙；
- 实证样本印证：iter-9 回复给出的"换个宿主"不是可执行动作；iter-13 则违反红线直接枚举了 `ppt-agent:*` 子代理清单并把用户推向违规模拟选项。

### 问题三：机器词表全旅程裸奔（覆盖面第一）

- 五字段英文蛇形块被位置合同锁定在**每条非纯内容回复的最顶部**（安全审计诉求，属合同本体）；
- `status`（advise/ready/blocked/paused/completed）与 `execution_eligibility`（allowed/blocked/retryable/unknown）两套近义词汇并存，组合语义靠用户自行合成；
- 约 350+ 个 reason code 的恢复措辞呈双峰分布——带具体命令的尚可，涉及 runtime/fingerprint/receipt 的是工程师便签体（抽查实证）；
- 最终交付回复照列 `runtime/upstream/patch/lock identity` 等溯源串与"未运行验证清单"，普通读者读到的是免责声明体；
- 实证发现**码漂移**：iter-13 样本输出了合同中不存在的码 `acceptance_pending`（规范码为 `delivery_acceptance_pending`）——"稳定机器码"承诺在用户面前也会失真，且现行判官未检测。

## 2. 分旅程详细发现

### 2.1 黄金路径（首次触达 → 准备 → 确认 → 执行 → 交付）

| # | 发现 | 证据 | 性质 |
|---|---|---|---|
| G1 | description 以否定合同句为主体，用户第一屏读到的像条文不像能力介绍 | `SKILL.md:3` | 呈现（C1 已有意为之，仅提示正文配套） |
| G2 | 混合请求一律降级 advise："顺手把环境弄好"不算授权，最少 +1 轮往返且感知"不被听话"；随后缺少一步切换的合法通道提示 | `SKILL.md:49-51` | 门禁必然成本 + 缓冲缺失 |
| G3 | 凭据录入是全程唯一离场操作（复制绝对路径命令→开 Terminal→TTY 向导→回报），只有命令没有人话包裹（为什么/会发生什么/做完说什么） | `first-use.md:61-64` | 安全必然成本 + 包裹缺失 |
| G4 | `configured_unverified`/`provider_verification_not_run` 等直出；blocked 分支的"不要倾泻内部名词"保护未覆盖这类"可用但未验"态 | `SKILL.md:132-137`、`first-use.md:32-36` | 呈现缺口 |
| G5 | 执行期（prepare→dispatch→record→QA 打回→assemble 可达数分钟至十几分钟）**没有任何进度播报要求**，成败信息延迟到终局一次性砸出 | `image-deck-workflow.md:15-27` 无播报条款 | 呈现空白 |
| G6 | 交付必报项（含 identity 串与 not-run 清单）无人话解读相伴；"OCR not-run"体感像免责声明 | `execution-contract.md:52-56` | 披露义务必然成本 + 版式缺失 |
| G7 | `status=completed 但 delivery_readiness=acceptance_pending` 双层语义反直觉；好消息排在机器块之后 | `SKILL.md:117-119` | 概念混淆 |
| G8 | "除纯内容创作外"输出五字段的边界未定义——确认轮格式抖动，一致性风险 | `SKILL.md:95` | 定义缺口 |

正面基线（须保持）：launcher/setup 对用户全自动、四态阻塞话术的单一 next_action 纪律在每个合规样本中都得到贯彻、`style_not_found`/`backend_contract_exists` 类恢复指引给出可照做的具体命令。

### 2.2 失败与阻断路径（合同面 + 6 份实证样本）

| # | 发现 | 证据 |
|---|---|---|
| F1 | worker-unavailable 死局（详见结构问题二） | `SKILL.md:154-169` + iter-9/13 实证 |
| F2 | Gate 0 触发时合同口径为零解释冷漠；实证样本（iter-13/untrusted-office-input）自行补上"文件完全未被触碰"+两条编号出路后成为全场最高分文案——证明人性化补充与安全合同可以共存，但其合法性未被合同承认 | `SKILL.md:14-16` vs 实证样本 |
| F3 | reason code 恢复措辞双峰分布；约半数属工程师便签体 | `reason-codes.md` 抽查 10 类 |
| F4 | 码漂移实证（`acceptance_pending` 非规范码）且无判官校验 | iter-13/delivery-acceptance-pending |
| F5 | 临时绝对路径（`/private/var/folders/...`）与防御性元叙述进入用户可见文案 | iter-13/14 多份样本 |
| F6 | best-in-class 失败文案要素已被实践验证：判决先行（"材料没有到达。"）、引用用户原话锚定、进度保全式安抚（列出已替你完成的事项）、单一行动指令——但这些都靠模型自由发挥，未沉淀为合同资产 | iter-14 实证 |

### 2.3 交互设计与行业对照

主流创作工具公式是"少问多给，生成后改"：一次性推断所有可推断项，唯一保留的人工门是产物级"看到再改"，备选项吸收进产物而非前置问答。本合同的差异不在门的存在（质量合同），而在三点：门之间**必须串行逐轮**的保守解读、视觉方向给了 2–3 个选项却没有"推荐项+一键采用"语义、backend 这类基础设施概念被暴露为用户决策点。upgrade-selected 还要求用户对可能多次变化的失败页集合反复做精确口头确认，工作记忆负担高，而"什么算精确接受"的表达下限未定义。

## 3. 优化建议

> 所有建议的设计边界：不削弱 Gate 0 阻断、样张门、真实派发、completed≠闭环四条硬约束；建议形态以**加法与重组**为主（披露不改条目集、解释区不加锁、模板不复述）。Q = 合同零改动可直接落地；P = 需要修改合同文本语义，实施前应拍板；E = 评测体系配套。

### Q 档：合同零改动快赢（呈现层）

| # | 建议 | 落点 | 解决 |
|---|---|---|---|
| Q1 | **合并确认轮明示化**：在 workflow 中写明"相邻确认内容可在同一回复中打包给出、等待一并答复"，并要求主动预告剩余门的数量与顺序（预期管理）。门的存在性不变，消灭"一轮一门"的额外税 | `image-deck-workflow.md` | 问题一 |
| Q2 | **视觉方向改为"推荐前置"**：2–3 个方向必须显式标注推荐项及一句话理由，声明"同意推荐只需回复确认" | `image-deck-workflow.md:12` | 问题一 |
| Q3 | **执行期进度契约**：父 Agent 每次 record 后向用户播报"N/M 页完成；打回重做 X 页（原因一句话）"——将 slide-worker 返回中已有的 qa_note 信息转译给用户 | `execution-contract.md` Worker 节 | G5 |
| Q4 | **状态人话映射表**：为 status × delivery_readiness 组合定义固定中文短语（ready→准备就绪即将开始；paused→暂停等你 X；completed→成品已生成、验收尚未完成），要求解释区首句使用映射短语 | `SKILL.md:110-119` 附近 | 问题三/G7 |
| Q5 | **终端凭据步骤人话包裹模板**：规定离场指令的标准三件套——为什么不能在聊天里输入、执行时会看到什么、完成后回来发哪句话 | `first-use.md` 安全凭据动作节 | G3 |
| Q6 | **交付报告分层版式**：用户层在前（交付类型、PPTX 路径、已通过的验证、距闭环还差什么、唯一下一步），审计层在后标注附录（identity 串、恢复产物、not-run 明细）。条目集一项不减，只重组顺序 | `execution-contract.md:52-56` | G6/问题三 |
| Q7 | **"纯内容创作"边界定义**：明确大纲/逐页稿/样张确认属于内容创作交流，免五字段块；状态变化节点（blocked/paused/completed/交付）才触发 | `SKILL.md:95` | G8 |
| Q8 | **advise 一步切换话术**：混合请求降级时，回复末尾必须附预置切换语（"回复『开始执行』即进入执行"），把 +1 轮的挫败压缩成一句 | `SKILL.md:49-51` 附近 | G2 |

### P 档：合同语义微调（需拍板后实施）

| # | 建议 | 权衡点 |
|---|---|---|
| P1 | **Gate 0 中性补充句合法化**：明确允许在固定块之后追加两类内容——"文件完全未被触碰"安心句、两条合法出路（可信确认/改用 PDF）的中性指引；仍严禁响应净化/扫描/绕过类指令 | 实证证明价值巨大，但当前合同口径是最冷酷版本；放开需仔细划界防社工话术渗入 |
| P2 | **worker 死局的用户侧出口**：保持禁诊断红线不变，但在固定块后的解释区规定最低限度人话缓冲——承认该限制、说明已冻结内容不受影响、给出用户视角出路（在有子代理能力的宿主重开会话 / 联系宿主管理员）。钉死两个不许：不许点名或计数宿主内的任何代理类型，不许提议主 Agent 代跑 | 红线与缓冲之间的措辞空间需要精确定义，否则判官红线会被变体绕过 |
| P3 | **backend 确认"默认选定+异议即改"语义**：registry 自动选定后向用户用人话披露（用什么图源、是否产生费用），仅并列/缺能力时升级为提问。注意这实质修改了"确认图片 backend"不变边界的语义——默认沉默视为确认 | 决策成本显著下降 vs "沉默=确认"引入误授权风险；需要明确表态 |
| P4 | **高频码最小暴露面**：user-facing 场景限定约 30 个高频码，其余罕见码统一以"内部错误 <code>"形式转译；为高频码建标准人话短语库（新增 `references/reason-code-glossary.md` 或扩展 `render-control-summary.py --fixed` 家族提供带注输出版本，注解置于块后不碰位置合同） | 翻译层厚度 vs 全量透明原则 |
| P5 | **upgrade-selected 接受语模板化**：把"明确接受"的下限写成封闭式话术（"确认：失败 N 页保留原图交付"并复述页 id 清单），展示清单+复用同一模板，消除解析歧义 | 降低用户记忆负担；话术刚性可能显得机械 |

### E 档：评测体系配套

| # | 建议 | 说明 |
|---|---|---|
| E1 | **reason code 保真断言**：新判官校验回复中出现的每个 reason code 都在 canonical 枚举内（可在 Python 中硬编码码表正则），直接针对 iter-13 实证的 `acceptance_pending` 漂移 | 现有判官只测指定码在场，不测冒名码 |
| E2 | **术语暴露度抽检**：对交付/失败类用例增加弱断言——用户解释区出现 `patch`、`lock identity`、`fingerprint`、临时目录绝对路径等项时给 warning 级记录，先观测再决定是否升格 FAIL | 避免又一组恒定 FAIL 污染套件信号 |
| E3 | **best-practice 正例沉淀**：iter-14 的四要素（判决先行/原话锚定/进度保全/单步指令）提炼进 case 的 judge 描述或 fixture 注释，作为后续人工复核参照基线 | 把偶然的优秀样本变成可复核标准 |

## 4. 实施顺序建议

1. **第一批（Q1/Q2/Q8 + E1）**：收益最大、风险最低、且与既有评测闭环兼容——合并确认轮、推荐前置、一步切换话术、码保真判官。
2. **第二批（Q3–Q7）**：呈现层模板与人话映射，纯增法。
3. **拍板后（P1/P2/P4/P5）**：P2 worker 死局缓冲优先级最高（伤害最大场景），但其措辞边界必须先过判官红线兼容性论证。
4. **暂缓观察（P3，E2 升格）**。
5. 全部落地后按惯例跑全量评测并在 known-issues 记账；建议同时推进待办中的官方 Claude 模型全量跑——UX 层面诸多"模型自由发挥垫付"的现状（Gate 0 补充句、优秀失败文案）依赖模型能力，换基线会改变这些结论的成立条件。
