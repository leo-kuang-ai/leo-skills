实践半年多，说几个真实感受，先讲结论：**SDD 最大的价值不是让 AI 写出更好的代码，而是让"完成"这个词重新有了定义。**

我的场景：日常在 Claude Code 和 Codex 里干活，写一个开源的工程化 harness（叫 spec-first，文末有）。痛点大家都熟——AI 五分钟回你"完成了"，测试全绿，diff 干净，但你不敢合并。不是不信任模型，是说不清它按什么顺序做的、哪些要求被悄悄忽略了。

SDD 之后我的工作流变成三段：

**第一段，想清楚。** 一句话想法先过 brainstorm，收敛成 requirements-only 计划：需求（R）、功能点（F）、验收标准（AE）。这一步禁止讨论实现——听起来反直觉，但大部分返工都来自"没想清楚就开写"。

**第二段，规划好。** 在同一份文档上补 HOW：拆实现单元、写依赖和验证门禁。关键设计是单一真相源——后面从计划派生的任务包，源计划一变就作废，永远不存在两份漂移的文档。

**第三段，做出来。** 按当前源码执行，本地验证不可跳过，留下 diff、测试和验证证据。

真实体验里最有价值的是第三段的约束：**完成声明受证据约束**。验证缺失、失败或者含糊，就不算完成。我自己的项目现在每个交付都带一张"Decision Receipt"：凭什么说完成、哪里还可能错、证据在哪里。比如官网一个页脚计数器：需求四条（公开计数、优雅降级、基础防刷、不采 IP/UA）、6 个实现单元、10 项 node:test + 6 项 Playwright 全过，还显式保留 2 个未验证边界——不包装成完成。

也说缺点，不讲趣味童话：

1. **仪式感成本是真实的。** 改一行 CSS 也走全套流程就是自虐。我的做法是分级：小活直接写，大活才上链。SDD 不是宗教。
2. **前期速度一定变慢。** 想清楚阶段多花的 20 分钟，是从后面省出来的，但你会先感到慢。
3. **对 prompt 工程师是降维打击（不客气地说）。** 靠把规矩越写越长塞进系统提示词的路子，在这套体系面前就是人肉维护一份没人读的说明书。

要不要试：如果你每天重度用 AI 写代码、被"AI 说完成但我不知道它干了什么"折磨过，SDD 值得投入一个周末。如果只是偶尔让 AI 写个脚本，没必要。
