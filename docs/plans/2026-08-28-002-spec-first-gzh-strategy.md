## 一、战略锚点

### Target problem

微信侧的开发者读者正在被约 386 篇第三方转述喂养着理解 spec-first，官方账号在公网零存在
（搜狗未收录，官网只挂了二维码）；同时概念科普已经泛滥，但没有一个中文源讲
「怎么在 Claude Code/Codex 里真正跑起来」。读者拿到的是转述而非设计意图，纠偏成本随时间累积。

### Our approach

只写一手实践：每篇文章必须来自仓库里真实跑通的工作流、版本或案例，用官方源定义
spec-first 这个词——不追热点、不转述、不写通用 AI 资讯。

### Who it's for

**Primary:** 重度 AI Coding 个人开发者——每天在 Claude Code/Codex 里干活的人。
他们关注这个号是为了「让 AI 写的代码敢合并」：拿到可照抄的工作流和真实踩过的坑。

### Key metrics

- **打开率** — 常读粉丝中点开文章的比例；公众号后台，每篇可看（先行指标）
- **在看 + 分享率** — 内容质量代理信号；后台，能回归、能证伪
- **阅读原文点击** — 文章 → GitHub/官网引荐流量；后台「阅读原文」或 utm 链接
- **微信群周净入群** — 读者变社区成员的转化；群管理
- **常读用户数** — 滞后指标，季度看趋势；公众号后台

### Tracks（内容三轨）

1. **概念定义权** — 官方立场文：spec-first 与 spec-driven/SDD/Spec Kit 的区别、五条规则中文阐释。
   为什么：赛道已有讨论度但无官方坐标系，此时定义成本最低。
2. **实战流水线** — 把 spec-* 工作流逐个拆成可照抄的中文实践（brainstorm → plan → work → review 全链）。
   为什么：打法承诺的核心供给；别人只能转述，作者能写设计决策。
3. **版本与增长回路** — release 中文解读 + 官网/GitHub/微信群互导。
   为什么：产品持续迭代 = 选题不断粮；账号是漏斗不是孤岛。

### Not working on

- 不做通用 AI 资讯和热点转述
- 不承诺日更（产品节奏是周级，兑现不了的写进简介就是透支信任）
- 不买量、不互推引流

### Marketing

**One-liner:** 从想法到可验证代码的 AI Coding Workflow——官方中文频道。

## 二、执行计划

### 2.1 账号基建（第 1 周）

- 三件套按 `gzh-positioning` 方法论产出（草案见 2.4），逐项过字数校验后贴后台。
- 冷启动期菜单只上两格（跑起来 / 找我们），「读什么」攒够 3 篇必读后再上——
  空菜单比没菜单伤害更大。
- 生产工具链：gzh-Skills 装入宿主技能目录；用作者 3 篇已发全文 + 标题清单
  生成**本人文风档案**（替换空格的键盘的 my-voice.md，方法照搬）。
- 配置 `REDFOX_API_KEY`（选题日赛道数据）。

### 2.2 发布节奏

- 前 8 周：**双周 1 篇长文 + 每周 1 篇短文**（保频率不透支质量；单人运营 + 产品并行）。
- 第 9 周起按数据评估升到周更长文（条件：长文生产流水线跑顺 ≥3 次）。
- 每周一选题（赛道数据 + 版本动态 + Issue 池），周中写作，发布前走包装四连：
  `baokuan-title-generator` → `space-gzh-cover` → `space-chart-image`/`space-text-logic-diagram`
  → `space-wechat-layout`。
- 每篇只带一个出口：阅读原文指向 GitHub，或文末群码。

| 周 | 动作 | 产出 |
|---|---|---|

| W2 | 首发 | 长文①《spec-first 不是 Spec Kit：一个词的三种含义》+ 短文⑧ 实操观察 |

选题池（按三轨滚动补充）：② 五条规则系列（1/5）、⑤ spec-work 验证证据、⑥ spec-debug

「官方补充」类短文冷启动期性价比最高。

### 2.4 三件套草案（带字数校验）

**简介 A 版（读者收益型，82 字，限 120）：**

> 重度用 Claude Code 或 Codex 写代码的人在这。每篇内容都来自 spec-first 仓库真实跑通的
> 工作流，AI 说"完成"不算数，要证据。

**简介 B 版（身份供给型，71 字，限 120）：**

> spec-first 作者本人运营。写 AI Coding 工作流怎么落地：需求、计划、执行、评审、证据，
> 全部留在仓库里。每周一篇，只写跑通过的。

>
> 先读这三篇：

> 【此处放：quickstart 实录文链接】从安装到第一个 green PR

**菜单树（冷启动两格版）：**

```
跑起来(3)            找我们(3)
├ 快速开始(4)        ├ 微信群(3)
├ 工作流(3)          ├ GitHub(6)
└ 版本解读(4)        └ 提需求(3)
```

字数校验：一级菜单 2 个，均 3 字 ≤4 ✓；二级最多 3 个，GitHub 为 6 字母（≤16 字节）✓，
其余均 ≤4 字 ✓。简介 A 82 字、B 71 字 ≤120 ✓；关注回复约 240 字 ≤600 ✓。

### 2.5 增长回路

```
文章(定义权/实战) → 搜一搜 & 第三方文章评论区占位 → 读者装产品 → Issue/反馈 → 下篇素材
                  ↘ 阅读原文 → GitHub star ↗
                  ↘ 文末群码 → 微信群 → 深度用户/案例
```

### 2.6 90 天路线图

| 阶段 | 目标 | 关键动作 |
|---|---|---|
| 0–30 天 | 基建 + 首发 4 篇 | 三件套上线、①③④+2 短文发出、文风档案建立 |
| 31–60 天 | 供给稳定 + 被搜到 | 攒到 8–10 篇、搜一搜关键词占位（spec-first / AI Coding 工作流）、第一波群沉淀 |
| 61–90 天 | 回路转动 | 第一个用户案例文、用打开率数据复盘选题类型、官网 Versions 页与账号互链 |

### 2.7 红线（从产品基因继承）

- 不编造数据、案例、用户反馈——账号与产品共用 Evidence over confidence。
- 不写兑现不了的更新承诺。
- 高风险标题（绝对化、未证实对比）不做综合首选，交 `baokuan-title-generator` 风控规则把关。

## 附录 A：W1 长文全文初稿

**标题 A（推荐）**：《Spec-First 全景：17 个 workflow 怎么串成一条链》
**标题 B（A/B 用）**：《AI 说"完成"的时候，让它拿出证据》

---

昨晚把一个需求扔给 Claude Code，五分钟它回我"完成了"。测试全绿，diff 干净。

我还是没敢合并。

不是不信任模型，是我说不清它按什么顺序做的、哪些要求被它悄悄忽略了、什么才算"做完"。

AI Coding 最大的问题不是写错代码。是会话一关，意图就没了。

你为什么这么设计、放弃了哪些方案、验收标准是什么——这些东西只活在当次的对话里。下个会话，另一个 Agent 要从零猜。

多数人的解法是把 prompt 越写越长。所有规矩塞进系统提示词，结果是人肉维护一份没人读的说明书。

真正缺的不是更长的 prompt。是一条链：每个阶段留下可以被下一阶段检查的东西。

spec-first 把这条链做成了 17 个 workflow、35 个 source skills、26 个 agents。听起来很多，串起来就三段。

第一段，想清楚。spec-ideate 和 spec-brainstorm 把一句话想法收敛成 requirements-only 计划——只回答 WHAT，禁止讨论怎么实现。

我自己最容易犯的错，就是没想清楚就开写。这条链会直接拦住你。

第二段，规划好。spec-plan 在同一份文档上补 HOW：拆实现单元、写验收标准，升级成 implementation-ready。大活再加 spec-write-tasks 编译成任务包——源计划一变，任务包就作废，永远只有一个真相源。

第三段，做出来。spec-work 按当前源码执行，留下 diff 和测试；spec-code-review 出结构化评审意见；验证门槛收证据；最后 spec-compound 把踩过的坑沉淀成可检索的经验。

三个阶段，回答三个问题：要什么、怎么算做好、凭什么说完成。

说到"凭什么信"——官网页脚那个访问量计数器，本身就是一条真实交付链。所有产物固定回源 commit b6261910，点开就能看。

需求写的是"公开计数、优雅降级、基础防刷、不采集 IP/UA"，四条在代码里各有落点。计划拆成 6 个实现单元。验证是 10 项 node:test 加 6 项 Playwright。

最有意思的是：它保留了 2 个"未验证边界"，没有包装成完成。独立 task pack、不同部署环境的会话策略，页面上一条条列着。

页面上还有个 Decision Receipt，三个问题都能点开：凭什么完成？哪里还可能错？证据在哪里？

我的判断：这比"AI 帮我写了十万行代码"有价值得多。前者是可以被质询的工程记录，后者是不可复核的表演。

也说清楚它不管什么。

spec-first 不承诺 AI 永远正确。它做的事是让每个判断有上下文、每次交付有验证、每个残余风险有明确位置。

三种情况不需要它：一次性 prompt 用完就扔；仓库禁止写入；指望一个中心化平台管流程。它是个 harness，不是平台——执行永远发生在你本地，Claude Code 和 Codex 负责写代码，它负责保留意图、约束范围、用证据管住"完成"这个字。

它还要你改一个习惯：先写需求，再动手。等代码写完再补 spec，链就断了。

回到开头那个不敢合并的夜晚。

问题不在 AI，在我没有一个"完成"的公认定义。spec-first 把这个定义变成链上的证据：需求、计划、代码、评审、验证，全留在仓库里。

打开方式一条命令：

npm install -g spec-first

然后到你的仓库里跑 spec-first quickstart。
