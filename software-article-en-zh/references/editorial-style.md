# 中文技术运营编辑规则

本规则只在 `delivery_mode: polished` 或 `publication`（默认）时生效。它约束表达，不改变原文事实、技术关系、责任主体或规范性强度。`publication` 的六阶段流程、五件套交付与合取判定见 `publication-delivery.md`。

两档的增量边界：`polished` 执行“编辑顺序”与“表达规则”全部条目（清除英文句法、调整节奏、统一术语、上下文化产品机制术语）；`publication` 在此之上再执行“产品与运行时术语”的受众适配、标题/段落/隐喻优化与“发布前检查”清单（可结合 `audience` 与 `register`）。标题与隐喻的主动优化属于 `publication`；`polished` 只做不改写语义的自然化微调。

## 编辑顺序

1. 先确认保真初译已经保留否定、条件、因果、量词、数字、风险和限制。
2. 再处理中文句法、段落节奏、标题和隐喻。
3. 最后检查是否引入原文没有的事实、承诺、评价或营销语气。

## 表达规则

- 优先使用自然的中文主谓结构，避免逐词映射英文长句。
- 英文长句可以拆分，但拆分后必须保留原有逻辑关系和语气强度。
- 被动句可以改为中文主动句，但不得改变责任主体。
- 抽象名词可以转换为中文动词，前提是不改变技术含义。
- 面向开发者的文章优先使用行业通行表达，不追求文学化或夸张化。
- 口语、隐喻和宣传语按上下文转写；保留观点，不照搬导致误解的字面意象。

## 产品与运行时术语

- 产品名、模型名、文件名、API 名和代码标识保留官方写法。
- 宿主机制或运行时术语首次出现时保留英文标识并给出最小中文解释，例如“上下文压缩（compaction）”。
- 后续使用统一简称，不用普通词替代会造成机制误解的术语。

## 编辑越界

以下任一行为按审校问题 `issue_type: editorial_overreach` 记录（七类问题之一，定义见 `review-rubric.md`），触发回退或重润：

- 新增原文没有的事实、例子、数据、因果、承诺或结论；
- 把 may / can / could / might / suggest 等弱化表达强化为确定性（"会""一定""保证"）；
- 把建议（SHOULD / recommend）改成要求（必须），或把限制（MUST NOT / cannot）改成保证；
- 改变责任主体、条件方向、否定辖域或量词强度；
- 借术语解释、标题优化、隐喻转写之名补充原文没有的背景或判断。

## 发布前检查

- 标题准确、自然，并与正文范围一致。
- 段落有清晰的主题推进，避免英文连接词残留。
- 中文读者可以直接理解，但不应因此补充原文没有的背景或结论。
- `technical_review` 与 `editorial_review` 分开报告；编辑润色通过不等于完成独立审校。
