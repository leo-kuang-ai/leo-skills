# 产品与营销文案

用于落地页、产品介绍、Hero、CTA、引导语、邮件标题、Onboarding 和产品状态文案。不要用于个人署名长文或技术参考文档。

## 路由

- 没有现有文案：`write`。
- 已提供文案：`edit`；只点名一行时做局部修改，不扩成整页审计。
- 错误、成功、空状态、加载、权限或危险操作：`state-copy`，优先准确说明状态、后果和下一步，不使用营销说服框架。

## 写前合同

写作前必须确定或显式标记推断：

1. 页面要推动的唯一动作；
2. 具体读者、痛点及已经尝试过什么；
3. 产品做什么，以及给读者带来的可观察结果；
4. 流量入口与温度：冷广告、暖邮件、自然搜索、推荐等；
5. 页面类型、品牌声音和必要证明材料。

错误推断会让整份文案失效或直接发布时，先询问；否则列出推断后继续，便于用户基于具体候选修正。

## 新写流程

1. 用一句话冻结价值主线：`[读者] 可以 [完成结果]，不再 [旧阻碍]`。
2. 优先读取现有品牌/声音文件和已上线文案；没有时使用临时品牌语域。
3. 按情况选择框架：陌生冷流量用 Why/How/What，功能密集用 Benefit-not-feature，需要具体证明用 Show-don't-tell，长销售页可用 PAS，明确交易场景强调 CTA clarity。
4. 页面、Hero 或 Campaign 给 3 个结构不同的方案；单个 CTA 或邮件标题给 2 个。方案必须真正改变角度，不是替换形容词。
5. 每个方案包含适合该载体的完整文案；推荐一个并用一句话解释，其余方案各给一个具体改进条件。
6. 逐行检查：具体结果、证明、行动、事实来源、品牌声音和上下文是否一致。

框架服务于真实目标，不强制所有文案都「先讲 Why」。已知意图的热流量或产品状态文案可以直接说 What/How。

## 编辑流程

先选择姿态：

- `point-edit`：只改目标与最少连接文本；
- `restore`：已有清晰声音和定位，修复具体失败；
- `rebuild`：文案通用、矛盾或没有价值主线，允许重构但不得编造证明。

按影响标记问题：产品功能而非用户结果、形容词无证明、价值模糊、语态或声音漂移、没有命名真实痛点、死文字、专业黑话、主张无证明、CTA 不明确、状态/后果不清、AI 模板痕迹。只报告 3-7 个最影响转化或理解的问题。

输出 `Before / Issues / After / Why`。每项改写必须修复已命名的问题；只是不同而没有更好时恢复原文。所有原始事实、数字、链接和限定条件必须保留。

## 产品状态文案

- 错误：说明发生了什么、原因（已知时）和可执行下一步，不责怪用户。
- 成功：按结果大小表达，通常简短。
- 空状态：说明当前状态和可开始的动作。
- 加载：需要等待时说明正在做什么，不作虚假承诺。
- 权限/危险操作：明确对象、范围、不可逆后果和取消路径；按钮不能只写「确定」「OK」。

## 退出条件

每一行都服务于唯一动作或必要状态；功能已翻译为具体结果；所有证明可追溯；CTA 表达结果或明确动作；品牌声音一致；去模板修改没有删除真实具体信息。
