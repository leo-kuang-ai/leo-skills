# 技术文档

用于编写或审查教程、操作指南、参考资料和解释文档。技术文档的完成标准是读者能正确完成任务或查到准确事实，而不仅是读起来顺。

## 先按 Diataxis 分类

每个文件选择一个主类型并命名受众：

- **Tutorial 教程：**带学习者从零完成一个可验证结果，按学习路径组织。
- **How-to 操作指南：**帮助已有上下文的用户完成具体目标，按任务步骤组织。
- **Reference 参考：**准确、完整、可扫描地描述 API、配置、参数和行为。
- **Explanation 解释：**说明为什么、机制、权衡、历史和概念关系。

不得混用类型要求。例如解释文不强求 Quickstart，参考文不承担从零教学。

## 写作流程

1. 冻结文档类型、目标读者、前置条件、预期结果和实现版本。
2. 从源码、Schema、CLI help、官方接口或实际运行结果建立事实清单，不凭记忆写参数。
3. 按类型组织：教程强调连续学习路径；How-to 直接完成目标；Reference 按稳定查询结构；Explanation 组织机制与权衡。
4. 结论先行，术语稳定；一个概念至少给一个可运行或可验证例子（不适用时说明）。
5. 自审声音、结构、清晰度、代码、格式、导航、可扫描性和内容卫生。
6. 执行验证门禁。

## 验证门禁

发布前必须在当前环境允许的范围内：

- 运行每个代码和命令示例，记录命令、环境和结果；
- 解析每个内部链接，检查外部链接当前可访问性；
- 将参数名、字段名、默认值、错误码和返回结构与当前实现或官方 Schema 对照；
- 验证前置条件、文件路径、版本和预期输出；
- 对无法执行的示例明确标记 `not_run` 和原因，不得推断为通过。

示例失败时返回源码、示例或文档拥有者修复，不能只润色描述。fixture 通过不能外推为所有平台或线上环境通过。

## 审查输出

按文件报告，严重度从高到低：

```markdown
### path/to/doc.md
- [CRITICAL] code-example：命令使用了不存在的参数 `--foo`。
  - 证据：当前 CLI help 只包含 `--bar`。
  - 修复：改为 `--bar` 并重新运行示例。
```

每条 finding 必须有规则、证据和可执行修复。没有 finding 的文件也标记通过。仅审查请求不得修改文档；要求修复时，修复后重跑命中的规则和示例。
